1. WHAT THIS PROJECT IS
-----------------------

A hand-curated, link-only catalog of C and C++ programming material from about
2000 to 2010 that is STILL LIVE on its original website today.

Think: a university OS course from Fall 2004 whose project pages still load,
with Bochs, gcc 3.x, CVS and tar.gz submission instructions. Or a 2006 hobby
page that walks you through writing a Lisp interpreter in C. The reader should
open the link today and see what a student or hobbyist saw back then.

Good topics: operating system kernels, schedulers, thread libraries, file
systems, shells, memory allocators, garbage collectors, network servers and
protocols, routers, distributed systems, compilers, interpreters, virtual
machines, JITs, assemblers, linkers, emulators, simulators, database internals
(buffer managers, B+ trees, query engines, recovery), compression, Unix tools,
text editors, device drivers, embedded/microcontroller labs, parallel
computing (MPI, OpenMP, pthreads, early CUDA), crypto implementation, game
engines, rasterizers, ray tracers, audio/DSP.

Graphics, OpenGL and Win32 GUI material is already well covered. Add more only
when it is unusually strong.

THE LISP WING (since October 2026). Besides C/C++, the catalog accepts
projects where the reader WRITES LISP: Scheme (PLT/DrScheme/MzScheme, MIT
Scheme, Chez, Racket from 2010), Common Lisp, Emacs Lisp, Clojure
(2007–2010), AutoLISP and other dialects. Same rules: 2000–2010 date proof on
the page, live today, real projects (evaluators, interpreters, compilers in
Scheme, SICP/HtDP/EOPL/PLAI course projects, AI programs, games, editor
extensions, web apps). Tiny exercise sheets are out. No other languages.

3. THE TWO RULES EVERY ENTRY MUST PASS
--------------------------------------

RULE A — The material itself is from 2000–2010 (inclusive; the validator
rejects other years).
  The proof must be visible ON THE PAGE (or in its URL), for example:
    - an explicit date: "Due: May 2, 2002", "Last modified March 2004"
    - a semester: "Fall 2004", or a year-coded path: /fa04/, /2003/, /spring2002/
    - period tools: Visual C++ 6.0, .dsp/.dsw files, Visual Studio .NET 2003,
      Dev-C++, Borland C++, DJGPP, gcc 2.95/3.x/early 4.x, CVS, Fedora Core,
      Red Hat 9, Solaris lab machines, Bochs, Simics, Nachos, Pintos, GeekOS,
      SDL 1.2, Allegro 4, DirectX 7/8/9, SPIM, Linux 2.4/2.6, LLVM 1.x/2.x
  NOT proof: a modern copyright footer, a modern article saying "from 2004",
  a search-engine snippet, a GitHub README.

RULE B — The page loads live today, at its original or long-running address.
  - Never use web.archive.org (or any archive mirror) as the catalog URL.
    You may use the Wayback Machine only to investigate history.
  - Reject GitHub/GitLab-only sources, Medium, Dev.to, modern reposts,
    retrospectives and modern rewrites.
  - A modern page design is fine if the original period text is intact.

Also required:
  - The reader WRITES C or C++ (or, for the Lisp wing, a Lisp: see section 1).
    A course where students write the compiler in
    Java, ML, OCaml, Haskell or Python is out, even if the target is C. If a
    course says "C++ or Java", accept it only if C/C++ starter code or C/C++
    as the default is on the page.
  - It is a real project, lab, assignment, tutorial or substantial technical
    article. Not a syllabus with no projects, not a slide deck alone, not a
    one-page snippet.
  - Do not catalog exploit or attack labs (buffer-overflow exploitation,
    shellcode, malware). Defensive and crypto-implementation work is fine.
  - Not already in the catalog, and not a near-duplicate of something in it.
    At most 2 semesters of the same course in total, unless the content
    is clearly different.

Check existing semesters before you accept a course, for example:
  grep -i "cs414" cpp-web-archaeology/data/projects.json

When in doubt, reject. Put borderline pages in leads.md instead.


4. SCORE
--------

The score is how sure you are that the entry fits the archive. It is not a
grade of how good the course was.

  98–100  Museum grade: original dated archive, real project, clear C/C++/Lisp.
  95–97   Prime: very strong period evidence, clearly relevant.
  90–94   Solid: good material, slightly weaker proof or smaller scope.
  85–89   Borderline: add only with a clear reason, and say why in the PR.
  < 85    Never add.

Aim for 90 and above, but score honestly. Never raise a score to 90 just to
avoid explaining it. Caps:
  - Proof is only a period toolchain (no date, no semester): at most 94.
  - Undated page whose date comes only from a linked file or directory
    listing: at most 92.
  - Article or documentation (no build project): at most 95.


5. RECORD FORMAT
----------------

projects.json is one JSON list. Each new record has exactly these 12 fields:

{
  "title": "Cornell CS414 — User-level threads and semaphores",
  "url": "https://www.cs.cornell.edu/courses/cs414/2003su/projects/project1/project1.html",
  "year": 2003,
  "year_label": "June 2003",
  "language": ["C"],
  "category": "Operating Systems / Concurrency",
  "kind": "project assignment",
  "site": "cs.cornell.edu",
  "score": 99,
  "evidence": [
    "Original 2003 assignment",
    "C source skeleton",
    "Windows NT Minithreads environment"
  ],
  "tags": ["threads", "semaphores", "scheduler", "Minithreads"],
  "notes": "Build a non-preemptive user-level thread package with queues, thread control blocks, a scheduler and semaphores."
}

Field rules:
  title       "Institution COURSE — What you build", or "Author — Article title".
              Add the term when it helps tell semesters apart.
  url         The exact live URL you loaded. https if https works. No tracking
              parameters, no #fragment.
  year        Integer, 2000–2010.
  year_label  The most precise date the page shows ("Due 4 Nov 2003", "Spring 2005").
  language    List that includes "C" and/or "C++" (other entries like
              "x86 assembly" are allowed). Lisp wing: one or more of "Scheme",
              "Common Lisp", "Emacs Lisp", "Clojure", "AutoLISP", "Racket",
              "Lisp" (generic only if the dialect is unclear).
  category    Reuse an existing category when it fits (see the list from the
              stats script). Common ones: Operating Systems, Operating Systems /
              Concurrency, Filesystems, Systems / Unix, Systems / Memory,
              Networking, Networking / Protocols, Networking / Routing,
              Distributed Systems, Parallel Computing, Compilers, Compilers /
              Lexing, Compilers / Parsing, Compilers / Semantic Analysis,
              Compilers / Code Generation, Compilers / Optimization,
              Compilers / JIT, Interpreters / Virtual Machines, Assemblers /
              Linkers, Emulators, Architecture Simulators, Database Internals
              (/ Buffer Manager, / Indexing, / Query Processing, / Recovery),
              Device Drivers / Linux Kernel, Embedded Systems, Compression,
              Cryptography, Text Editors, Graphics / Algorithms, Ray Tracing,
              Games / Engines, Audio / DSP. Create a new one only if it will
              hold several records.
              Lisp wing records MUST use a "Lisp / ..." category:
              Lisp / Interpreters & Evaluators, Lisp / Compilers, Lisp / Intro
              Courses, Lisp / Programming Languages, Lisp / AI, Lisp / Games &
              Graphics, Lisp / Web & Applications, Lisp / Emacs & Editors,
              Lisp / Tutorials & Books. A Lisp interpreter written IN C stays a
              C record (Interpreters / Virtual Machines), not Lisp wing.
              Lisp-wing tags always include "lisp" and the dialect.
  kind        Exactly one of: project assignment, project sequence, course
              project sequence, lab assignment, lab sequence, tutorial,
              tutorial series, project tutorial, source-code project, source
              project, course archive, tutorial archive, technical article.
  site        The URL's host without "www." (must match the URL).
  score       See section 4.
  evidence    3 to 6 short strings. Each one a concrete fact you saw on the page.
              At least one must be a short VERBATIM quote of the date proof,
              in double quotes, e.g. "Due: Thursday, October 7, 2004".
  tags        3 to 7 search words. Include the words a reader would use for the
              project type ("kernel", "compiler", "filesystem", "sockets",
              "B+ tree", "MPI"...). The site's "What do you want to build?"
              tiles match on title, category, notes and tags.
  notes       One or two plain sentences: what the reader builds.

Do not add any other fields.

7. WORKFLOW
-----------

Step 1 — Look at the gaps.
  python3 $SKILL/scripts/catalog_stats.py --urls-out $WORK/existing_urls.txt
  python3 $SKILL/scripts/catalog_stats.py --categories
  Pick areas that are small, years that are thin, and leads that are open.
  If the owner gave you a focus (for example "compilers"), stay on it.
  Size: a good batch is about 10–40 new records. Fewer is fine if the area
  is thin. Do not pad.

Step 2 — Research.
  If you can run parallel sub-agents, give each one a separate domain and its
  own output file in $WORK/batch/. Otherwise work through domains one by one.
  Methods that work:
    - Search with period fingerprints, not generic phrases:
        site:edu "operating systems" "project 3" "Fall 2004"
        site:edu inurl:fall05 filesystem "Makefile"
        "Visual C++ 6.0" ".dsw" assignment
        site:edu "you will implement" "buffer manager" C++
    - FOLLOW DIRECTORIES. When a page is strong, open its course index,
      sibling projects, sibling semesters and the instructor's other course
      archives. One good page often leads to ten. This beats searching.
    - Hosts that keep year-coded archives live include cs.cmu.edu,
      cs.princeton.edu/courses/archive, cs.cornell.edu/courses,
      pages.cs.wisc.edu, classes.cs.uchicago.edu/archive, cs.columbia.edu,
      cseweb.ucsd.edu/classes, scs.stanford.edu, pdos.csail.mit.edu,
      users.ece.utexas.edu, cs.usfca.edu/~cruse. Many are already well
      represented: prefer NEW institutions and NEW sites.
    - Check every candidate yourself: load it, find the date evidence, confirm
      C/C++ (or Lisp), and grep $WORK/existing_urls.txt for its host.
    - Web search budgets are limited. When yours runs low, switch to following
      directories with curl.
  Write results to $WORK/batch/<name>.json in this shape:
    {
      "accepted": [ <records in the format of section 5> ],
      "rejected": [ {"url": "...", "reason": "short reason"} ],
      "borderline_leads": [ {"url": "...", "note": "why worth a later look"} ],
      "investigated_count": 0
    }

Step 3 — Merge and review.
  python3 $SKILL/scripts/merge_batch.py --batch-dir $WORK/batch \
      --out $WORK/merged.json --report $WORK/report.json
  Read every merged record again with fresh eyes. Remove weak ones by
  re-running the command with  --drop URL [URL ...]  when:
    - the date proof is weak (only a footer, no date on the page),
    - it is a near-duplicate (third semester of a course, same text on two hosts),
    - the score is 85–89 and the scope is small.
  Spot-check at least 5 records yourself: re-load the page and confirm the
  quoted date proof is really there, e.g.
    curl -sSL URL | grep -i -o -m3 -E "due[^<]{0,30}|(fall|spring|winter) 20[01][0-9]"
  Do all --drop runs BEFORE step 4.

Step 4 — Verify live.
  python3 $SKILL/scripts/check_urls.py $WORK/merged.json --fix
  --fix switches http/https when only the other one works. It also flags
  REDIRECT when a page now lands on another host or on a site's front page
  (a "soft 404"): drop those. Drop anything that still fails. Exception: some servers (e.g. web.eecs.umich.edu) send an
  incomplete TLS certificate chain, so curl fails while browsers work. Never
  disable TLS verification. Fetch the missing intermediate certificate from
  the certificate's "CA Issuers" URL, add it to a CA bundle, retry with
  curl --cacert, and keep the record if it loads. check_urls.py will still
  print FAIL for such hosts; that is expected. List them in the PR.

Step 5 — Append and validate.
  python3 $SKILL/scripts/append_catalog.py $WORK/merged.json
  python3 $SKILL/scripts/validate_catalog.py        # must exit 0
  python3 $SKILL/scripts/catalog_stats.py           # see "matching NO intent tile"
  If a new record matches no tile, improve its tags/notes wording. Do not
  edit the website; mention it in the PR instead.

Step 6 — Update leads.md.
  Remove leads you added or proved dead. Add new leads from report.json
  ("leads") under the matching domain heading (create one if none fits), and
  new dead ends under "Known dead ends". Keep the format: "- URL — short note".

Step 7 — Commit, push the branch, open a pull request.
  git add cpp-web-archaeology/data/projects.json \
          .claude/skills/cpp-web-archaeology/references/leads.md
  git status --short          # only those two files may appear
  git commit -m "Add N curated <areas> archive entries"
  git fetch origin main && git rebase origin/main
  git push -u origin HEAD
  Then open a PR against main (gh pr create, or the GitHub web UI).

  If the rebase conflicts on projects.json: a weekly bot re-sorts that file.
  Keep main's version and re-append your records:
    git checkout --ours cpp-web-archaeology/data/projects.json
    python3 $SKILL/scripts/append_catalog.py $WORK/merged.json
    python3 $SKILL/scripts/validate_catalog.py
    git add cpp-web-archaeology/data/projects.json
    GIT_EDITOR=true git rebase --continue
  (During a rebase, "ours" means origin/main.)
